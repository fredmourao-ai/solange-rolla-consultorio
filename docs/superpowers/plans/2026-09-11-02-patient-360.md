# Onda 1 — Paciente 360° e Navegação — Plano de Implementação

> **Execução:** usar `superpowers:subagent-driven-development`, TDD e worktree isolado por task. Não implementar em `main` diretamente.

**Spec:** `docs/superpowers/specs/2026-09-11-solange-end-to-end-operational-design.md`
**Índice:** `docs/superpowers/plans/2026-09-11-00-solange-end-to-end-execution-index.md`
**Dependência:** Onda 0 — permissões por rotina concluída e mergeada.

## Objetivo

Transformar o cadastro genérico de `people` em uma experiência centrada em **Pacientes**, sem quebrar o registro único interno, e criar uma ficha 360° que seja o ponto de entrada para Secretaria e Profissional. A ficha deve reunir contexto administrativo, consultas, formulários, documentos, financeiro e, quando autorizado, acesso ao prontuário.

## Regras de arquitetura

- A tabela/entidade interna `people` permanece como registro único; a UX principal usa **Pacientes**.
- Dados clínicos não podem ser adicionados à tabela administrativa `people`.
- Campos pessoais devem ser minimizados ao necessário para a operação do consultório.
- Permissões mínimas: `patients.read`, `patients.create`, `patients.update`, `patients.archive`, `patients.relationships.manage`.
- Toda página/Server Action valida permissão no servidor; ocultar botão/menu é apenas conveniência de UX.
- Contabilidade não ganha acesso amplo a `people`; usa read model fiscal mínimo quando autorizado.
- Testes/fixtures somente com pessoas sintéticas.

**Validação focal:** testes de componentes + Playwright de navegação em desktop e mobile.

## Task 2 — Evoluir modelo administrativo do paciente

**Criar migration forward-only** para os campos administrativos realmente necessários que ainda não existirem. Preferir colunas normalizadas quando houver regra/consulta e JSON somente para estrutura fiscal compatível existente.

Campos-alvo, após reconciliar com schema atual:
- telefone alternativo opcional;
- contato de emergência: nome, vínculo, telefone;
- profissão/ocupação opcional;
- origem/indicação opcional e não clínica;
- status administrativo do paciente (`active`, `inactive`, `archived`) se ausente;
- modalidade/frequência padrão somente se pertencente ao acompanhamento administrativo; não guardar demanda/objetivos clínicos aqui.

**Não adicionar:** diagnóstico, queixa/demanda, objetivos terapêuticos, anamnese, notas de sessão, testes psicológicos ou qualquer texto clínico.

**RLS:** preservar default-deny e substituir políticas baseadas somente em role por checks de permissões da Onda 0 quando aplicável.

**RED DB:**
- secretaria autorizada consegue ler/editar campos administrativos;
- usuário sem `patients.read/update` não consegue;
- `accounting` não obtém contatos/histórico desnecessários;
- nenhuma nova coluna clínica aparece em `public.people`.

## Task 3 — Formulário reutilizável de criação/edição

**Modificar/criar:**
- `src/modules/people/ui/person-form.tsx`
- testes do formulário
- Server Actions/pages de `/pessoas/novo` e `/pessoas/[personId]/gerenciar`
- `src/modules/people/application/update-person.ts` e contrato público somente se necessário.

O mesmo componente de formulário deve operar em `create` e `edit`, carregando valores atuais na edição.

Seções de UX:
- Identificação: nome civil, nome preferido/social, nascimento, CPF;
- Contato: telefone/WhatsApp, telefone alternativo, e-mail;
- Endereço/fiscal: CEP, logradouro, número, complemento, bairro, cidade, UF;
- Emergência: nome, vínculo, telefone;
- Preferências administrativas: canal, aniversário, origem/indicação;
- Responsáveis/vínculos em seção própria.

**RED:** editar um paciente sintético existente, salvar, recarregar página e verificar valores persistidos.

**Requisitos:**
- normalização CPF/e-mail/telefone no domínio;
- erro de duplicidade apresentado em linguagem humana;
- validação sem mensagens técnicas;
- botão e action exigem `patients.update`.

**Modificar:**
- `src/app/(protected)/pessoas/page.tsx`
- `src/modules/people/application/search-people.ts`
- `src/modules/people/ui/person-search.tsx`

**Comportamento:**

- cada resultado mostra nome preferido/civil, contato principal, status e próxima consulta quando disponível;

**RED:** pesquisar um paciente sintético por CPF e localizar exatamente seu card; paginação preserva query; usuário sem leitura recebe 403/redirect seguro.

## Task 5 — Ficha 360° / read model

Criar um read model de aplicação que reúna somente dados permitidos ao usuário e não force a página a consultar tabelas de módulos diretamente de forma desorganizada.

**Novo contrato sugerido:**
- `src/modules/people/application/get-patient-hub.ts`
- tipos públicos mínimos em `src/modules/people/public.ts`
- página `src/app/(protected)/pessoas/[personId]/page.tsx` ou evolução da rota existente.

**Resumo administrativo:**
- identidade e contatos;
- idade/data de nascimento;
- última e próxima consulta;
- quantidade de consultas realizadas;
- status do acompanhamento administrativo;
- pendências administrativas permitidas;
- completude fiscal;
- responsáveis/vínculos.

**Abas:**
- Resumo;
- Cadastro;
- Consultas;
- Formulários;
- Documentos;
- Financeiro;
- Comunicação;
- Prontuário apenas quando `clinical.read` + papel clínico + AAL2.

O read model não deve descriptografar conteúdo clínico para construir o resumo administrativo.

## Task 6 — Responsáveis e vínculos

Reutilizar `person_relationships` para responsável legal, financeiro e tomador fiscal. Evoluir UI para:
- localizar/cadastrar pessoa relacionada sem duplicar registro;
- informar tipo de vínculo;
- substituir/remover vínculo com auditoria;
- impedir auto-vínculo e duplicidade.

Permissão: `patients.relationships.manage`.

Testes negativos devem garantir que usuário sem a permissão não consegue mutar vínculos por Server Action ou acesso direto permitido pelo cliente.

## Task 7 — Acompanhamento administrativo mínimo

Se ainda não houver entidade adequada, criar `care_episodes`/`therapy_engagements` em módulo compatível, contendo apenas metadados administrativos:
- paciente;
- profissional responsável;
- status `active|paused|completed|discontinued`;
- início/fim;
- modalidade;
- frequência planejada;
- serviço padrão.

**Conteúdo clínico (demanda/objetivos/evoluções) fica fora desta tabela.**

A ficha mostra acompanhamento atual e históricos encerrados, sem confundir um retorno futuro com continuação automática do processo anterior.

## Task 8 — Integração contextual e E2E da Onda 1

Criar E2E de Secretaria e Profissional com dados sintéticos:

```text
Secretaria login
-> Pacientes
-> Novo paciente
-> preencher cadastro
-> salvar
-> abrir ficha 360
-> editar telefone/endereço
-> salvar
-> refresh
-> confirmar persistência
-> criar responsável financeiro
-> abrir Consultas
```

E teste de segurança:

```text
usuário sem patients.read
-> menu Pacientes ausente
-> GET /pessoas rejeitado/redirecionado de forma segura
-> tentativa de Server Action/update rejeitada
```

## Critério de saída

A Onda 1 só termina quando Secretaria consegue administrar um paciente sem entrar em telas técnicas, a Profissional consegue abrir a mesma ficha com sua visão autorizada, e um usuário sem permissão é bloqueado tanto na UI quanto no servidor/banco.
